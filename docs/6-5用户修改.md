## 二、远线 bug 修复

### 现象与原因链

问题出在 `cross.cpp`。每次进入 `cross_evolve` 都会先清空：

```cpp
rt->cross.left_l  = -1;
rt->cross.right_l = -1;
```

然后重新做远线识别。如果某一帧的远线能够找到，但因为某种原因 L 并没有识别出来，这两个数就还是 -1。

对应的判断在第 399 行：

```cpp
if (rt->cross.right_num >= k_cross_min_front_step && rt->cross.right_l >= 0)
```

我本来考虑删掉 `rt->cross.track_type = TRACK_TYPE_NONE;`，但发现仍然避免不了这个情况。因为就算保留 `track_type`，链路还是会断：

```text
保留 track_type
  -> 知道该跟左 / 右
  -> 但 left_l / right_l 还是 -1
  -> solve_cross_mid() 不知道从远线哪里开始生成中线
  -> mid_ok = 0
  -> TRACK_REJECT_NO_MIDLINE
  -> control input invalid
  -> 停车
```

### 远线扫描结构

先把远线的扫描结构理清楚：

```text
固定列 far_x1 = 86
  -> 从 begin_y 往上扫，找白后黑边界
  -> seed = (far_x1, far_y1 + 1)
  -> findline_lefthand_adaptive() 左手追线
  -> far_ipts0    原图远线点列
  -> mapx / mapy  透视变换
  -> far_rpts0
  -> blur
  -> far_rpts0b
  -> resample
  -> far_rpts0s
  -> local_angle + nms
  -> 扫角点
  -> far_Lpt0_rpts0s_id
```

### 我的修改

这里的处理改成更直接的状态语义：

- `left_l` / `right_l`：本帧找到新 L 就覆盖；本帧没找到新 L，旧值可以暂时保留。
- `left_far_found` / `right_far_found`：标记当前帧远线点列是否构建成功。

> [!note]
> // 构建左右十字"远线"（通常为前方远 L 点串），存状态标志到 left_far_found / right_far_found
> rt->cross.left_far_found  = build_cross_farline(rt, 1);
> rt->cross.right_far_found = build_cross_farline(rt, 0);
> 它内部有一个 *far_l = -1。

还要加一个边界检查，避免旧 id 套不到当前帧的新远线上：

- `left_l = 30`，但当前帧左远线只有 `left_num = 20` 个点 -> 这个旧 id 必须被覆盖。
- 旧 `left_l = 18`，当前帧 `left_num = 22`，后面只剩 4 个点，而最低需要 6 或 8 个点：

```text
left_num - left_l < k_min_border_step
```

这种也不能用，否则 `left_pts[left_l]` 会越界。

### 三种情况

1. **找到 L 点** -> 覆盖。
2. **没找到 L 点，但当前帧有远线** -> 这是这次要修的核心。
   当前帧 `left_pts` 有点、`left_num` 足够，但 `far_l_index()` 返回 -1。这时不要立刻 `left_l = -1`，而是看旧 id 能不能套在当前新远线上：
   - 旧 `left_l >= 0`
   - 旧 `left_l < 当前 left_num`
   - `当前 left_num - 旧 left_l >= 最小点数`

   都满足就继续用旧 `left_l`；不满足才 `left_l = -1`。注意这不是"覆盖"，而是"储存"（保留旧索引）。
3. **都没找到** -> 全部清理。

### 对 gpt 五项建议的取舍

我把之前那五个修改重新过了一遍。结论是：前五个我都不接受。我不兜底，一切都直白了，先保证对应单例能够成功。逐项说明：

- **第 3 项｜cross.cpp 远线失败兜底选边** → 已采纳（窄版）。
  已经做了更窄的版本，也就是第二个提交"修复十字远线丢失停车"。它不是简单兜底选边，而是"当前远线存在时复用旧 L 索引"，更安全。
- **第 1 项｜control.cpp 3 帧才清积分** → 暂不做。
  风险偏高，它是在控制层掩盖视觉失败。除非确认只是偶发坏帧，否则不建议先做。
- **第 2 项｜BEGIN->IN 不截 rpts** → 待判断。
  可能有用，但和当前代码里"BEGIN 先截近线"的逻辑冲突。需要先判断停车是不是发生在刚切 IN 的那一帧。
- **第 4 项｜ring.cpp 环岛 3 帧确认 + RUN 超时** → 下一阶段重点。
  最值得作为下一阶段研究：环岛目前没有成功案例，而且状态误判 / 卡 RUN 都可能解释现象。
- **第 5 项｜trace 失败不清零部分数据** → 借鉴，不照搬。
  太宽，容易复用旧边界。可以借鉴，但不应全局照搬。

## 四、mainline 第一阶段收口（历史实现说明）

本节记录 mainline 第一阶段收口时的实现说明。后续 Stage 7 已经继续整理命名和合同：当前源码用 `frame_action_t`、`frame_mode_t`、`base_candidates_ready`、`snapshot_ring_frame_start_action()`、`apply_frame_start_element_crop()`、`build_zebra_scan_midline()` 等名字；下面提到的局部变量名和行号按当时阶段理解，恢复当前上下文时应以源码符号搜索为准。

这一轮最后决定不继续扩大到 `cross.cpp`、`ring.cpp`、`element.cpp`、`types.hpp` 或 `control.cpp`，主线收口只改 `code/tracking/mainline.cpp`。

核心不是做缓存，也不是兜底补丁，而是把 `tracking_process_frame()` 的后段顺序收成一条项目内部能讲清楚的合同：

```text
seed / trace
  -> build rpts + corners
  -> 记录 element_process() 前的普通选边和 ring 当前帧动作
  -> element_process()
  -> 本帧决定 cross far / cross near / ring / ordinary
  -> 统一生成中线
  -> 统一 gate
  -> 统一写 track_type / center_x / guide_error / zebra
```

### 为什么要改

旧结构里有三处半截问题：

1. `CROSS_IN` 远线有独立 early return，和普通 / ring 后段分裂。
2. 圆环选边读的是 `element_process()` 之后的 post state，转换帧可能提前切到下一阶段。
3. 最终短中线放行只围绕 `in_cross`，没有覆盖 ring，所以环岛仍然可能因为中线短或 hard lookahead 不够而停车。

现在的内部合同是：`ring.cpp` / `cross.cpp` 只推进元素状态，`mainline.cpp` 决定当前帧 source / side / crop，最后统一做中线、门槛和输出。

### 实际代码修改

主要改动点：

- 新增 `k_element_min_mid_step = 3`，表示元素态最短中线点数；普通帧仍使用 `k_min_border_step` 和 hard lookahead。
- `solve_cross_mid()` 保留远线总点数和远 L 点要求，但把 L 后剩余点门槛从 `k_min_border_step` 收到 `3`。
- `cross_in0` 改成 `cross_state0`，用本帧开始时的 cross state 区分：
  - frame-start 已经是 `CROSS_STATE_IN`，且 post 仍是 `IN` -> 走 farline。
  - 同帧 `BEGIN -> IN` -> 仍走近线裁剪，不立刻要求 farline。
- 在 `element_process(rt)` 前只保留本帧要用的局部事实 / 动作：
  - `ordinary_track_type0`
  - `ring_track_type0`
  - `ring_run_crop_side0`
  - `ring_run_crop_index0`
- cross near 帧继续裁 `rpts0s_num / rpts1s_num` 到当前近线 `now_step`。
- ring 当前帧 side 在 `element_process(rt)` 前就折算成 `ring_track_type0`：
  - 左环：`BEGIN/RUN/END` 走右线，`IN/OUT` 走左线。
  - 右环：`BEGIN/RUN/END` 走左线，`IN/OUT` 走右线。
- ring RUN 裁剪只用 element 前算出的裁剪动作：
  - 左环 RUN：`ring_run_crop_side0 = TRACK_TYPE_RIGHT`，裁右线 `rpts1s_num`。
  - 右环 RUN：`ring_run_crop_side0 = TRACK_TYPE_LEFT`，裁左线 `rpts0s_num`。
  - 不用补对侧边界 helper 之后的边界结果反推控制点列；当时名为 `build_opp()`，当前源码名为 `build_ring_opp_for_detection()`。
- 删除 cross farline 独立 early return，改成共同 midline block：
  - cross farline -> `solve_cross_mid(rt, ref)`。
  - 其它情况 -> `track_leftline()` 或 `track_rightline()`。
- 最终 gate 合并成一套：
  - 普通帧：`k_min_border_step` + `midline_has_lookahead()`。
  - 元素帧：`>= 3`，跳过 hard lookahead，由 `lookahead_error()` 自己 clip。
- writeback / zebra 合并成一套：
  - 成功后统一写 `reject_reason`、`track_type`、`track_type_keep`、`center_x`、`guide_error`。
  - cross farline 仍保持旧语义：`zebra_process(rt, nullptr)`，不强行构造 zebra scan。

### ring 相比基础版本的改进

这里的“基础版本”指 git 提交 `3015b4b 基础版本`。

- `ring.cpp` 本体只做了一个小修：当时文档名为 `build_opp()` 的补对侧边界逻辑，在没有当前边界点时，补边起点从跟随的 `mid_position` 改成稳定几何中心 `MID_X`，避免搜索中心漂移污染环岛补边。当前源码名是 `build_ring_opp_for_detection()`。
- 主要改进在 `mainline.cpp` 对 ring 的消费方式：
  - 基础版在 `element_process()` 后读 post `rt->ring.state`，转换帧可能提前切到下一阶段。
  - 当前版在 `element_process()` 前先算 `ring_track_type0`，当前帧按“刚刚运行的 ring 分支”选边。
  - 基础版 RUN 只裁 `boundary_t`，但最终中线读 `rpts0s/rpts1s`；当前版把 RUN crop 动作落到真正的 `rpts` 点数上。
  - 基础版 ring 仍吃普通中线长度和 hard lookahead；当前版把 ring 纳入元素帧 gate，短中线也能输出。
